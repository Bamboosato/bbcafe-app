# Gemini 3.5 Flash-Lite移行設計

## 1. 目的

BB Cafe Messagesのメッセージ生成について、主系を`gemini-3.5-flash-lite`、フォールバックを`gemini-2.5-flash`へ変更する。

対象は手動生成とCronによる自動生成の共通サーバー処理とする。プロンプト、生成結果の保存、LINE送信、画面表示の仕様は変更しない。

## 2. 現状と決定事項

### 2.1 現状

- `GEMINI_MODEL`を主系、`GEMINI_FALLBACK_MODELS`を後続候補として使用する。
- 一時的なHTTPステータス（429、500、502、503、504）の場合だけ、モデルごとに設定回数を再試行して次の候補へ進む。
- 現在のリクエストは全候補モデルに同じ`generationConfig`を送っている。
- 現在の設定は`temperature: 0.8`、`thinkingConfig.thinkingBudget: 0`。
- 自動送信Cronは`generateDailyGreetingMessage`を呼び出すため、手動生成と同じモデル切替を受ける。

### 2.2 採用する設定

```env
GEMINI_MODEL=gemini-3.5-flash-lite
GEMINI_FALLBACK_MODELS=gemini-2.5-flash
```

コード上のデフォルト値と`.env.example`も同じ順序に合わせる。デプロイ環境のEnvironment Variablesは実装検証後に更新する。

### 2.3 採用理由

- 3.5 Flash-Liteは低遅延・高スループット向けで、短い挨拶文生成の主系候補として適合する。
- 2.5 Flashは現行主系であり、既存の生成品質と互換性を持つフォールバックとして扱いやすい。
- フォールバックは通常経路ではないため、コスト最小化よりも生成継続性と品質を優先する。
- 3.5系では`temperature`などのサンプリング設定を削除し、`thinkingLevel`を使用する必要があるため、環境変数だけの変更にはしない。

## 3. リクエスト生成設計

### 3.1 モデル別プロファイル

候補モデルをループする際に、モデルごとに生成設定を構築する。プロンプトと`contents`は候補間で同一にし、モデル別に変えるのは`generationConfig`だけとする。

| モデル | `maxOutputTokens` | 思考設定 | `temperature` | 意図 |
| --- | ---: | --- | --- | --- |
| `gemini-3.5-flash-lite` | 300 | `thinkingConfig.thinkingLevel: "minimal"` | 送信しない | 短文生成の低遅延を優先しつつ、3.xの標準設定に合わせる |
| `gemini-2.5-flash` | 300 | `thinkingConfig.thinkingBudget: 0` | `0.8` | 現行フォールバックの挙動をできる限り維持する |

3.xリクエストには`temperature`、`topP`、`topK`、`thinkingBudget`を含めない。2.5系リクエストには`thinkingLevel`を含めない。

### 3.2 実装境界

既存の責務を次のように維持する。

```text
generateDailyGreetingMessage
  -> 共通プロンプトを作成
  -> モデル候補を順番に処理
  -> モデル別generationConfigでRESTリクエストを作成
  -> 一時エラーだけ再試行・次候補へ切替
  -> 既存の応答検証・重複判定・保存処理へ返す
```

`generateGeminiContent`にJSON化済みの単一`body`を渡す方式は、候補モデルごとにモデル別設定を適用できる方式へ変更する。候補ごとに同じプロンプトを再生成せず、入力内容の差異が発生しないようにする。

### 3.3 モデル候補の解決

- 候補順は`[主系, フォールバック1, ...]`を維持する。
- 重複モデルは既存どおり1回にまとめる。
- 空文字、空要素は候補に含めない。
- 対象の2モデル以外を環境変数で指定した場合は、既存のカスタム設定を壊さないため、2.5系互換設定を既定とする。ただし3.xモデル名を指定した場合は3.x設定を使う。
- 将来モデルを追加する際に設定差異を見落とさないよう、モデル判定と生成設定の対応を1か所に集約する。

## 4. フォールバック状態遷移

| 状態 | 条件 | 次の動作 | 意図 |
| --- | --- | --- | --- |
| 主系送信 | `gemini-3.5-flash-lite`へ送信 | 成功なら終了 | 通常経路を1回で完了する |
| 主系一時失敗 | 429/500/502/503/504 | 設定回数まで同じモデルを再試行 | 瞬間的な混雑を吸収する |
| 主系再試行上限 | 再試行後も一時失敗 | `gemini-2.5-flash`へ切替 | 送信機会を残す |
| フォールバック成功 | 2.5 Flashが成功 | 成功結果を既存処理へ返す | UI・Cronの後段を変えない |
| 全候補一時失敗 | 全モデルが上限まで失敗 | 既存のエラー履歴・通知処理へ返す | 無限再試行を防ぐ |
| 非一時エラー | 400等 | 既存どおり即時失敗 | 不正な設定や契約違反をフォールバックで隠さない |

モデル切替は同一生成試行内で行う。生成済みテキストを別モデルへ渡して再編集することはしない。

## 5. テスト観点

ケース作成前に、次の観点を受入れ対象とする。

### 5.1 機能観点

- 主系が3.5 Flash-Lite、フォールバックが2.5 Flashの順で呼ばれること。
- 主系成功時に不要なフォールバックを呼ばないこと。
- 一時エラー時だけ再試行・切替し、非一時エラーは即時失敗すること。
- 手動生成と自動送信Cronが同じ切替ルールを使うこと。
- 既存の天気、誕生日、記念日、直近の冒頭文制約が両モデルに同じ内容で渡ること。

### 5.2 非機能観点

- 3.5系リクエストに非推奨の`temperature`や`thinkingBudget`が混入しないこと。
- 2.5系フォールバックに`thinkingLevel`が混入しないこと。
- 再試行回数、`Retry-After`、遅延設定が既存どおり機能すること。
- 主系成功時のリクエスト数、フォールバック時の総待ち時間、エラー率を比較できること。
- APIキー、プロンプト全文、生成本文を新たなログへ出力しないこと。

### 5.3 データ観点

- モデル切替によってプロンプトの天気・カレンダー情報が欠落、重複、改変されないこと。
- 生成結果の保存先、日付、`lineAccountId`、送信履歴の関連付けが変わらないこと。
- フォールバック成功時も成功結果として扱い、失敗履歴を誤登録しないこと。
- 全候補失敗時に既存の部分結果・エラー要約を維持すること。

### 5.4 UI観点

- 手動生成画面の成功、失敗、再生成制御が変わらないこと。
- Cron完了通知と失敗通知の文面・件数が変わらないこと。
- フォールバックした事実をユーザー本文へ混入させないこと。

## 6. テストケース

前提として、APIキーはテスト用の値、天気・Firestore依存はモック、同一テスト内の`fetch`は逐次呼出しとする。外部APIの実呼出しやLINE送信は単体テストで行わない。

| ID | 区分 | ケース | 検証意図 |
| --- | --- | --- | --- |
| G-001 | 正常系 | 主系3.5 Flash-Liteが成功 | 新しい主系が正しいURLと3.x設定で1回だけ呼ばれることを確認する |
| G-002 | 正常系 | 主系成功後の呼出し数 | 成功時に2.5 Flashへ不要なフォールバックをしないことを確認する |
| G-003 | 正常系 | 2.5 Flashフォールバック成功 | 3.5系の一時失敗後、2.5系設定で成功結果を返すことを確認する |
| G-004 | 異常系 | 429/500/502/503/504 | 各一時ステータスが再試行・候補切替の対象であることを確認する |
| G-005 | 異常系 | 400/401/403 | 非一時エラーがフォールバックで隠されず、既存の表示要約になることを確認する |
| G-006 | 異常系 | 全候補が一時失敗 | 最終ステータスとエラー要約を保持して終了することを確認する |
| G-007 | 境界値 | 再試行回数0、1、異常値 | 余分な呼出しや無限再試行が発生しないことを確認する |
| G-008 | 境界値 | 空のフォールバック設定、重複候補 | 主系だけ、または重複除去後の順序で動作することを確認する |
| G-009 | リクエスト | 3.5系設定 | `thinkingLevel: "minimal"`のみを送り、`temperature`と`thinkingBudget`を送らないことを確認する |
| G-010 | リクエスト | 2.5系設定 | `temperature: 0.8`と`thinkingBudget: 0`を送り、`thinkingLevel`を送らないことを確認する |
| G-011 | データ | 主系失敗後の再送 | 天気・予定・直近冒頭文のプロンプトが候補間で同一であることを確認する |
| G-012 | 状態遷移 | 主系再試行→フォールバック成功 | 途中失敗から最終成功へ遷移し、失敗扱いを残さないことを確認する |
| G-013 | 状態遷移 | 全候補失敗 | 成功保存・LINE送信へ進まず、既存の失敗処理へ遷移することを確認する |
| G-014 | 回帰 | 既存の生成本文検証 | 空本文、`MAX_TOKENS`、禁止された終了理由、冒頭重複の既存挙動を維持することを確認する |

## 7. 実行範囲と証跡

### 実装時に必須

- `src/features/messages/server/gemini.test.ts`の対象テストを更新・追加する。
- `npm run test -- src/features/messages/server/gemini.test.ts`相当の対象単体テストを実行する。
- `npm run typecheck`、`npm run lint`、`npm run build`を実行する。
- `fetch`の呼出し順、URL、リクエストボディのモデル別設定をテスト失敗時の証跡として残す。

### 本番切替前に必須

- 同一入力を両モデルへ与え、少なくとも通常時、予定あり、悪天候、直近文ありのケースを比較する。
- 日本語の自然さ、冒頭の時刻挨拶、事実誤り、文字数、重複、生成時間を評価する。
- Cronの実行確認はLINE送信を伴うため、対象ユーザー・未送信状態・実行日時を明示してから単独で行う。
- 実機ブラウザーE2Eの全件実施は不要。今回の変更はサーバー側生成モデルとCron経路が中心のため、対象単体テストと限定的なCron確認を優先する。

### 未実施範囲

- この設計段階ではソースコード、環境変数、デプロイ先の設定を変更しない。
- 実際のGemini API品質、料金、レイテンシーはAPIキー・本番相当データ・実行枠が必要なため、設計書作成時点では未検証とする。
- UIの見た目確認は対象外。ただし既存エラー表示とCron通知の回帰確認は実装後に行う。

## 8. ロールバック

品質低下、400エラー、レイテンシー悪化、フォールバック率増加が確認された場合は、環境変数を次へ戻す。

```env
GEMINI_MODEL=gemini-2.5-flash
GEMINI_FALLBACK_MODELS=gemini-2.5-flash-lite
```

ロールバックはプロンプト・保存データ・送信履歴を変更せず、モデル候補の設定だけを戻す。実装後は、ロールバック設定でも2.5系の既存テストが通ることを受入条件とする。
