# 確認ボタン・未確認通知 仕様

2026-10-06時点の実装を記載する。Web Pushの送り先は、同じLINEアカウントに紐づくアプリの通知登録端末であり、未確認者本人へのLINE再送は実装範囲外。

## 目的

自動送信または手動送信したLINEメッセージに対して、ユーザーが確認ボタンを押したかを記録し、未確認のユーザーがいる場合にアプリ利用者へWeb Push通知する。

LINEの既読状態はMessaging APIで取得できないため、本機能では「確認したよ👍」ボタンの押下を確認済みとして扱う。

## 対象

- 自動送信メッセージ
- 手動送信メッセージ
- 送信成功したユーザーのみ

送信失敗したユーザーは既存の送信履歴の失敗として扱い、未確認チェック対象にはしない。

## 確認ボタン

- 表示文言: `確認したよ👍`
- LINE Messaging APIのクイックリプライで表示する。
- 左側アイコン: `public/line/confirm-quick-reply.png`
  - 濃い緑の円、金色の縁、白いチェックマークのPNG
  - `APP_BASE_URL` またはVercelのデプロイURLからHTTPSの `imageUrl` を生成する
  - HTTPS URLを生成できない環境では、アイコンなしで送信する
- アクションはpostbackとし、`runId` と `userId` を含める。
- Webhookでpostbackを受け取ったら、該当ユーザーを確認済みに更新する。
- postbackの`userId`がWebhookの実送信元と一致しない場合は更新しない。

## 最新メッセージ優先

同じユーザーに複数回送信している場合は、最後に送信したメッセージのみを未確認チェック対象とする。

- 新しい送信が成功したら、ユーザー単位の確認対象を新しい `runId` で上書きする。
- 古い送信履歴は残すが、未確認Push通知の対象にはしない。
- 古い確認ボタンが後から押された場合、古い送信履歴は確認済みに更新してよいが、最新送信の確認状態は変更しない。

## データ

### sendRuns

既存の送信履歴。`targets` に確認状態を追加する。

- `confirmationStatus`
  - `pending`: 未確認
  - `confirmed`: 確認済み
  - `reminded`: 未確認通知済み
  - `not_required`: 確認対象外
- `confirmedAt`
- `reminderSentAt`

### confirmationTargets

ユーザー単位の最新確認対象。

パス:

```text
lineAccounts/{lineAccountId}/confirmationTargets/{userId}
```

主な項目:

- `lineAccountId`
- `userId`
- `userName`
- `runId`
- `mode`
- `sentAt`
- `status`
- `confirmedAt`
- `reminderSentAt`
- `updatedAt`

## 確認チェックCron

- Route: `/api/cron/check-unconfirmed-messages`
- Schedule: `0 4 * * *`
- JST: 13:00

13:00時点で最新確認対象をチェックし、確認済みと未確認を記録する。実際の送信時刻が遅れていても、送信から6時間経過しているかは判定しない。

- 確認済み: `status = confirmed`
- 未確認: `status = pending` または `status = reminded`

Push通知は `pending` の未確認対象がいる場合のみ行う。`reminded` は未確認として履歴に残すが、再通知対象にはしない。

## Push通知

`pending`の未確認対象がいる場合、同じLINEアカウントのアプリ通知登録端末へWeb Pushする。旧viewer/adminのログイン種別では分類しない。

- 1人: `○○○さんに未確認メッセージがあります`
- 複数人: `○○○さんほかN名に未確認メッセージがあります`

Push処理がスキップされなかった場合、対象を`reminded`へ更新し、同じ送信に対する通知を繰り返さない。現行実装では購読0件や全件送信失敗でも更新されるため、`reminded`は端末への到達を保証しない。VAPID未設定の`missing_web_push_config`では更新せず、`pending`を維持する。通知処理と確認対象更新は、同時Cron実行を排他するトランザクションではない。

確認チェック履歴は`lineAccounts/{lineAccountId}/confirmationReminderRuns/{runId}`へ保存する。Push件数は端末への送信成功数であり、未確認ユーザ人数とは異なる。全件失敗・一部失敗・設定不足も履歴の結果と理由で区別する。

確認チェックの実行結果はCron履歴に記録する。

- 確認済み件数
- 未確認件数
- 確認済みユーザー名
- 未確認ユーザー名
- Push通知件数
- Push通知失敗件数

## 未確認状態の手動リセット

ホームの`未確認をリセット`は`POST /api/confirmation-targets`を呼び、本人のアカウントの最新`pending`／`reminded`を`confirmed`へ更新する。対応する送信履歴の成功対象も更新し、応答の`resetCount`で人数を返す。確認済み・対象0件では新たな対象を作らない。

これはアプリ利用者による手動処理で、LINE受信者が確認ボタンを押した証跡とは区別する。ユーザ単位の最新対象以外の古い未確認配信まで一括処理する操作ではない。

## テスト観点

詳細ケースの前に、機能（確認・集計・通知・リセット）、非機能（別アカウント分離・同時実行・Push障害）、データ（最新runId・履歴・端末数）、UI（未確認数・通知表示・リセット中）を確認する。

| 区分 | 前提 | 検証意図 |
| --- | --- | --- |
| 正常系 | 配信成功対象、同じuserIdのpostback | 対応履歴と最新対象を確認済みにする |
| 異常系 | userId不一致、LINE配信失敗、Push全件失敗 | 不正確認・対象外を除外し、Push失敗時のreminded更新を実仕様として確認する |
| 境界値 | 対象0、購読0、VAPID未設定 | 通知件数と未確認人数、スキップと更新を区別する |
| 状態遷移 | 新配信後の古いボタン、reminded後の確認、手動リセット | 古いrunIdで最新状態を変えず、通知済みからも確認済みへ移れる |

実送信は専用対象・初期状態を固定して単独実行し、runId、requestId、確認時刻、Push結果を証跡に残す。

## ホーム画面での表示

ホーム画面では、未確認対象を最優先で表示する。詳細は `docs/home-screen-spec.md` に従う。

- 未確認メッセージは「送信したLINEメッセージに対して、相手が確認ボタンを押していないもの」とする。
- 未確認対象が1件以上ある場合だけ、ホーム上部に `未確認メッセージがあります` カードを表示する。
- 未確認対象が0件の場合、注意カードは表示しない。
- 未確認対応の導線は、未確認カード内の `送信履歴で確認` に集約する。
- ホーム上部の常設ショートカット `メッセージ作成`、`受信履歴を確認` は、未確認有無によって切り替えない。
- モバイルでは、未確認カードを常設ショートカットより上に表示する。
