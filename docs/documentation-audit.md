## 4. 実装の境界として記録した事項

以下は文書変更で機能を追加・修正したものではない。実装済みの保証を過大に記載しないため、現状を明示した。

- アプリCookieは署名・期限を検証する。Firebaseユーザー無効化を保護APIごとに再照会し、即時反映する処理はない。
- 内部アカウントはユーザー別だが、登録Channel IDの全アカウント一意性とTokenとの一致を検証する処理はない。
- 確認チェックは13:00 JSTの定時処理。個々の配信から6時間経過したかを判定しない。
- `reminded`はPush到達保証ではない。通知と状態更新を同時Cronに対して排他する仕組みはない。
- 同日自動配信の重複予約は防ぐが、中断した予約は`failed`／終了日時なしとして残り得る。
- 履歴カーソルは送信時刻のみ。同一時刻の大量データで全件のページ境界を保証する複合カーソルではない。
- 取得件数に上限があり、全データ無制限処理ではない。有効アカウント検索0件時は既定アカウントへフォールバックする。
- 期限切れ送信履歴の削除数はAPI応答へ返すが、統合Cron画面の受信削除サマリーには保存しない。
- ユーザ情報・最新確認対象・確認チェック履歴等を履歴期限と連動して削除する機能はない。
- 警報・特別警報の構造化と通常挨拶の注意報表示を分け、緊急通知は将来要件とした。

## 6. 再発防止

今回の不整合は、個別機能の仕様更新が全体設計・README・Preview手順へ反映されず、旧設計の現在形と後続の実装記述が併存したことに起因する。文書保守の観点不足として整理する。

今後は認証、ルート、API入力、データ保存、環境設定、送信・通知の保証範囲を変更したとき、READMEの機能一覧、詳細設計、該当機能仕様、Preview手順を同じ差分で更新する。過去の検証実績は日付・対象リリースを明記し、現在の実装状態と分ける。v2.0.0要件は天気・季節情報の変更範囲であり、全機能要件として扱わない。
