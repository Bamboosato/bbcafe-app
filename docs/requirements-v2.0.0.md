## 1. 背景と目的

BB Cafe Messagesは、LINE利用者へ日次の挨拶メッセージを送信する。メッセージには日付、名古屋の天気、最高気温、誕生花などを含める。

v2.0.0では、次の課題を解消する。

- 最高気温に翌日の予報値が混入する可能性がある。
- 季節だけを条件にした注意情報では、当日の雨、雪、風、凍結リスクを十分に表現できない。
- 熱中症対策の判定に、公式WBGTや公式アラートを利用したい。
- 感染症の増加傾向や気象庁の警報・注意報を、根拠を持つ外部情報として利用したい。
- 同じ感染症週報の注意情報が、毎日のメッセージに繰り返し表示される。
- 手動作成とCronで、外部情報の利用条件や履歴判定が分かれることを避けたい。

目的は、対象日を取り違えない構造化天気情報と、公式情報に基づく簡潔な注意喚起を、手動作成・Cronの共通処理として提供することである。

## 2. 対象範囲

### 2.1 対象

- 日本時間（`Asia/Tokyo`）を基準にした日次メッセージ生成
- 気象庁の対象日予報からの構造化天気情報の作成
- 環境省の名古屋地点WBGT予測・熱中症アラートの利用
- 気象庁の愛知県警報・注意報の利用
- 国立健康危機管理研究機構（JIHS）の感染症週報の利用
- 雨、雪、風、凍結、暑さ、感染症に関する注意情報の選択
- 管理画面の外部情報ON/OFF設定
- 手動生成、手動送信、Cron送信で共有する感染症注意情報の表示履歴
- アプリバージョン`2.0.0`への更新とGitHub Releaseタグ`ver2.0.0`

### 2.2 対象外

- 警報以上の情報を別メッセージで即時通知する緊急通知機能
- 医療機関の受診、診断、治療、服薬を判断する案内
- 感染症の流行を、季節や単一の数値だけで断定すること
- 名古屋市単独の感染症データ。公式データの粒度に合わせて愛知県を対象とする
- 外部情報の取得を環境変数で強制的に停止する緊急停止フラグ
- 外部APIの将来の仕様変更を自動的に吸収する仕組み
- 外部情報を利用したことを利用者へ別途表示する管理者向け監査画面

## 3. 利用者と処理経路

| 利用者・処理 | 役割 |
| --- | --- |
| 管理者 | 管理画面で外部情報の利用をON/OFFし、設定を保存する |
| 手動作成利用者 | メッセージ生成画面から対象日のメッセージを作成し、必要に応じてLINE送信する |
| Cron | 保存されたアカウント設定に従って、日次メッセージを生成・送信する |
| 外部情報取得処理 | 対象日の天気・WBGT・警報・感染症情報を取得し、構造化データへ変換する |

手動作成とCronは、同じLINEアカウントの設定、対象日コンテキスト、注意情報の判定処理を共有する。手動プレビューは送信ではないため、感染症注意情報の表示履歴を更新しない。

## 4. 機能要件

### 4.1 対象日の決定と天気情報

| ID | 要件 |
| --- | --- |
| FR-001 | 生成対象日は日本時間で決定し、日付、天気、最高・最低気温、降水確率、風情報、WBGTの参照日を同一の対象日にそろえること。 |
| FR-002 | 気象庁レスポンスの`timeDefines`と各配列を対応付け、対象日の値だけを採用すること。翌日の最高気温を当日の最高気温として採用してはならない。 |
| FR-003 | 最高気温は短期予報の対象日データを優先し、利用できない場合に週間予報の対象日データを利用すること。対象日の値が空欄の場合、翌日の値へフォールバックしてはならない。 |
| FR-004 | 天気概要、天気コード、最高・最低気温、降水確率、風情報を構造化して注意情報判定へ渡すこと。天気文字列を主たるデータ源として再解釈する場合も、構造化された対象日データを優先すること。 |

### 4.2 公式WBGTと暑さ対策

| ID | 要件 |
| --- | --- |
| FR-005 | 名古屋地点の公式WBGT予測（地点`51106`）から対象日のWBGT最大値を取得すること。対象日と一致する時刻列だけを集計すること。 |
| FR-006 | WBGTが31以上の場合は熱中症対策、28以上31未満の場合は暑さ対策、25以上28未満の場合は軽度の暑さ対策を候補にすること。25未満はWBGT由来の注意情報を追加しないこと。 |
| FR-007 | 環境省の熱中症特別警戒・警戒アラートを取得できる場合、WBGT数値より優先すること。特別警戒、警戒の種別を構造化して扱うこと。 |
| FR-008 | WBGT予測の取得に失敗した場合は、気象庁の天気情報による生成を継続すること。WBGT取得失敗だけでメッセージ全体を失敗させないこと。 |
| FR-009 | WBGTが利用できない場合の補助判定として、5〜9月の最高気温30度以上、または月を問わず最高気温33度以上の場合に暑さ対策候補を作成すること。 |

### 4.3 雨雪風・凍結リスク

| ID | 要件 |
| --- | --- |
| FR-010 | 当日の天気概要に雨、雪、みぞれが含まれる場合、または降水確率が50%以上の場合、足元注意候補を作成すること。 |
| FR-011 | 雪またはみぞれがあり、対象日の最低気温が0度以下の場合、雨雪による足元注意より優先して路面凍結注意候補を作成すること。 |
| FR-012 | 天気概要または風情報に強風、暴風、風雪等が含まれる場合、強風注意候補を作成すること。 |
| FR-013 | 気象庁の雷、大雨、強風、大雪、風雪等の公式注意報が利用できる場合、推測による雨雪風注意より優先して公式の種別と行動案内を用いること。警報・特別警報の種別も構造化して保持するが、通常挨拶の現行判定対象は注意報とする。 |
| FR-014 | 路面注意は、転倒予防や安全な歩行を促す一般的な表現とし、危険度を過度に断定しないこと。 |

### 4.4 感染症情報

| ID | 要件 |
| --- | --- |
| FR-015 | JIHSの最新感染症週報から、愛知県のインフルエンザと新型コロナウイルス感染症を対象にすること。 |
| FR-016 | 最新の3週分の愛知県の定点当たり報告数が取得でき、直近3値が連続して増加している場合だけ、当該感染症を増加傾向と判定すること。 |
| FR-017 | 報告週、公表日時、情報元URL、対象感染症を構造化し、公表から14日を超えた情報、地域欠落、数値不正、必要な週の欠落がある場合は注意情報を作成しないこと。 |
| FR-018 | インフルエンザと新型コロナウイルス感染症の両方が該当する場合も、感染症対策の注意情報1件にまとめること。 |
| FR-019 | 感染症注意文は、手洗い、体調不良時に無理をしない等の一般的な行動に限定すること。診断、治療、服薬の案内を含めないこと。 |

### 4.5 注意情報の選択とメッセージへの反映

| ID | 要件 |
| --- | --- |
| FR-020 | 注意情報の判定は、月だけの固定条件ではなく、対象日の天気、気温、降水確率、風、WBGT、公式注意報、感染症週報を組み合わせて行うこと。 |
| FR-021 | 注意情報には種別と優先度を持たせ、優先度の高い順に最大2件だけ採用すること。熱中症、感染症、路面、雨雪、風等が同時に該当しても、メッセージが過度に長くならないよう制限すること。 |
| FR-022 | `appendSeasonalCareInfo()` は、選択済みの注意情報を天気情報へ追加する責務とし、外部情報の取得や判定を担当しないこと。 |
| FR-023 | 注意情報の追加に失敗した場合でも、通常の挨拶、天気、誕生花など、取得済みの情報によるメッセージ生成を継続できること。 |
| FR-024 | 注意情報は生成モデルへのプロンプトに渡すが、外部情報の取得失敗、内部キー、実装上のエラーを利用者向け本文へ出力しないこと。 |

### 4.6 外部情報の利用設定

| ID | 要件 |
| --- | --- |
| FR-025 | 管理画面に「外部情報」のON/OFFトグルを表示し、LINEアカウント単位で保存できること。 |
| FR-026 | 外部情報ONの場合、感染症週報、環境省の熱中症アラート、気象庁の愛知県公式注意報を手動作成とCronに反映すること。気象庁から取得した警報・特別警報の種別は構造化して保持する。 |
| FR-027 | 外部情報OFFの場合、上記の追加外部シグナルを取得・反映しないこと。既存の気象庁天気情報と通常のWBGT予測による基本的な天気・暑さ判定は継続すること。 |
| FR-028 | 既存の設定データに`externalCareSignalsEnabled`が存在しない場合は`false`として扱うこと。既存利用者が意図せず外部情報ONになることを防ぐこと。 |
| FR-029 | 外部情報の有効化を環境変数で上書きする機能は持たず、管理画面に保存された設定を手動作成とCronの共通入力にすること。 |
| FR-030 | 設定取得に失敗した場合は外部情報OFFとして生成を継続し、設定障害だけでメッセージ生成全体を失敗させないこと。 |

### 4.7 感染症注意情報の間引き

| ID | 要件 |
| --- | --- |
| FR-031 | 感染症週報の同一性を、`情報元URL | 報告週 | 公表日時 | 対象感染症（ソート済み）`のキーで判定すること。 |
| FR-032 | 未表示のキー、または公表日時・対象感染症等が変わった新しいキーは、表示間隔制限なしに表示可能とすること。 |
| FR-033 | 同じキーの感染症注意情報は、前回のLINE送信から日本時間で3日未満の場合は抑制すること。3日経過後は再表示を許可すること。 |
| FR-034 | 表示履歴はLINEアカウント単位で保存し、手動作成とCronで共有すること。履歴にはキーと最終表示日時を保存すること。 |
| FR-035 | 手動プレビューでは表示履歴を更新しないこと。手動送信またはCron送信で1件以上のLINE送信が成功した場合だけ最終表示日時を更新すること。 |
| FR-036 | 一部のLINE送信が失敗した場合でも、1件以上が成功していれば感染症注意情報を表示済みとして記録すること。全件失敗の場合は記録しないこと。 |
| FR-037 | 表示履歴の読み書きに失敗しても、注意情報以外のメッセージ生成・送信を可能な限り継続し、エラーはサーバーログで追跡できること。 |

## 5. データ要件

### 5.1 天気・外部シグナル

注意情報判定へ渡す構造化データは、少なくとも次の項目を持つ。

| 項目 | 内容 |
| --- | --- |
| `weatherText` | 対象日の天気概要 |
| `weatherCode` | 対象日の天気コード |
| `maxTemperature` | 対象日の最高気温 |
| `minTemperature` | 対象日の最低気温 |
| `precipitationProbability` | 対象日の降水確率 |
| `windText` | 対象日の風情報 |
| `wbgtMax` | 対象日のWBGT最大値 |
| `wbgtAlert` | `warning`、`special`、または未該当 |
| `jmaWarnings` | 愛知県の有効な公式警報・注意報 |
| `infectionTrend` | 感染症名、報告週、公表日時、情報元URL |

外部シグナルは個別に取得し、取得できない項目は`null`または空配列として扱う。取得できた他の項目は引き続き利用する。

### 5.2 アカウント設定

既存の日次送信設定に次の項目を追加する。

| 項目 | 型 | 初期値 | 内容 |
| --- | --- | --- | --- |
| `externalCareSignalsEnabled` | boolean | `false` | 感染症週報、WBGTアラート、気象庁警報・注意報の利用可否 |

設定はLINEアカウント単位で保存し、手動作成APIとCron APIが同じ値を参照する。

### 5.3 感染症表示履歴

既存のアカウント単位の自動送信設定ドキュメントに、次の項目を保存する。

| 項目 | 内容 |
| --- | --- |
| `infectionNoticeKey` | 感染症週報の同一性キー |
| `infectionNoticeDisplayedAt` | 最後に1件以上のLINE送信が成功した日時 |

日時差の判定はカレンダー日単位で日本時間へ変換して行い、単純な経過時間だけで判定しない。

## 6. 外部情報源と取得条件

| 情報 | 情報源 | 主な取得条件 |
| --- | --- | --- |
| 名古屋の天気 | 気象庁の天気予報API | `timeDefines`が対象日と一致する配列要素を採用 |
| 名古屋のWBGT予測 | 環境省暑さ指数データ提供サービス、地点`51106` | 対象日の列だけを集計 |
| 熱中症アラート | 環境省アラートCSV | 愛知県の対象行を参照 |
| 愛知県警報・注意報 | 気象庁防災情報 | 愛知県エリアコード`230010`、発表・継続中のみ参照 |
| 感染症週報 | JIHS感染症サーベイランス | 最新週報、愛知県行、インフルエンザ／COVID-19、定点当たり報告数を参照 |

外部取得にはタイムアウトを設け、取得元ごとの失敗を分離する。感染症データはShift-JIS CSVを読み取り、週報の公表日時から14日を超える場合は無効とする。

## 7. 非機能要件

| ID | 観点 | 要件 |
| --- | --- | --- |
| NFR-001 | 可用性 | 外部情報源の一部障害で、通常の挨拶・天気・誕生花の生成まで失敗させないこと。 |
| NFR-002 | タイムゾーン | 日付・予報対象日・感染症表示間隔は日本時間で一貫して扱うこと。 |
| NFR-003 | 性能 | 外部情報取得を逐次待ち合わせず、独立した情報源は並行取得して全体の待ち時間を抑えること。 |
| NFR-004 | 安全性 | APIキー、LINE資格情報、生成プロンプト全文、生成本文を新たな診断ログへ出力しないこと。 |
| NFR-005 | 表現 | 注意文は高齢者にも理解しやすい一般的な行動案内とし、医療上の断定を避けること。 |
| NFR-006 | 後方互換性 | `externalCareSignalsEnabled`がない既存設定を読み込んでも、外部情報OFFで従来処理を継続できること。 |
| NFR-007 | 保守性 | 外部情報の取得、構造化、注意情報の優先度付け、メッセージへの追加を分離すること。 |

## 8. 受入条件とテスト設計

### 8.1 先に確認するテスト観点

- 機能観点：対象日、注意情報、トグル、手動／Cron、間引きが要求どおり連動すること
- 非機能観点：外部障害時の継続、タイムアウト、ログ、タイムゾーン、性能
- データ観点：予報配列の対応、公式データの鮮度、週報キー、表示履歴、旧設定の初期値
- UI観点：管理画面トグルの表示・保存・再表示、生成結果への反映
- 正常系：有効な天気・WBGT・週報・設定がそろう場合
- 異常系：一部取得失敗、CSV不正、設定取得失敗、送信失敗
- 境界値：WBGT 25／28／31、最低気温0度、降水確率50%、週報14日／15日、表示後0〜2日／3日
- 状態遷移：外部情報OFF→ON→OFF、プレビュー→手動送信、Cron送信、週報更新、部分送信成功

### 8.2 受入ケース

| ID | 区分 | ケース | 検証意図 |
| --- | --- | --- | --- |
| AT-001 | 正常・データ | 今日より明日の最高気温が高い | 今日の`timeDefines`の値だけが採用され、翌日の値が混入しないことを確認する |
| AT-002 | 境界・データ | 短期予報の今日の値が空欄、週間予報の今日の値が有効 | 今日の週間予報へフォールバックし、明日の値へずれないことを確認する |
| AT-003 | 正常・機能 | WBGTが25、28、31の境界 | 暑さ対策の境界と文面の優先度が正しいことを確認する |
| AT-004 | 異常・状態遷移 | WBGT取得がタイムアウトまたは503 | 気象庁の天気情報で生成を継続することを確認する |
| AT-005 | 正常・機能 | 雨、雪、降水確率50%以上、強風 | 当日の状況に応じた足元・風の注意が追加されることを確認する |
| AT-006 | 境界・機能 | 雪かつ最低気温0度、雨のみ、乾燥した寒日 | 凍結注意の過剰適用を防ぎ、雨雪注意と区別することを確認する |
| AT-007 | 正常・優先度 | 公式注意報と天気文字列による注意が同時成立 | 公式注意報を優先し、同種の注意を重複表示しないことを確認する |
| AT-008 | 正常・データ | 感染症の直近3週が連続増加 | 愛知県の対象感染症を増加傾向として1件にまとめることを確認する |
| AT-009 | 境界・データ | 感染症情報の公表から14日、15日 | 14日以内は利用し、15日以上は注意情報を作成しないことを確認する |
| AT-010 | 異常・データ | CSV文字化け、愛知県行欠落、週不足 | 感染症だけを無効化し、天気メッセージを継続することを確認する |
| AT-011 | 状態遷移・UI | 外部情報OFF→ON→OFF | 管理画面の設定が保存され、手動作成とCronへ同じ状態が伝播することを確認する |
| AT-012 | 境界・互換性 | 既存設定にトグル項目がない | 外部情報を誤って有効化せず、`false`として扱うことを確認する |
| AT-013 | 状態遷移 | 同じ週報を送信後0〜2日、3日 | 3日未満は抑制し、3日経過後に再表示できることを確認する |

## 10. 運用上の注意と将来検討

- 外部情報源のURL、CSV列、JSON構造が変更された場合は、取得失敗または情報欠落として注意情報を抑制し、取得処理とテストを更新する。
- 公式情報が取得できない日があっても、利用可能な通常天気情報で生成を継続する。取得できない情報を推測で補完しない。
- 感染症注意情報の表示間隔は現時点で3日である。利用者の負担や情報鮮度を確認して、週報更新時のみ表示する方式などを再評価できる。
- 気象庁の警報・特別警報は取得・構造化済みだが、現行の通常挨拶では注意報を表示判定の対象としている。警報以上を通常挨拶へ反映するか、緊急通知へ分離するかは別途要件化する。
- 警報以上の情報を通常挨拶へ含めるか、将来の緊急通知へ分離するかは、別要件・別送信経路として定義する。
- 本書は実装後の現行仕様を定義しているため、将来変更時は要件、設計、テスト、リリースノートを同一変更で更新する。
